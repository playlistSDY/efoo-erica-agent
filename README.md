# EFOO 한양 ERICA 학교 안내 RAG 에이전트

한양대학교 ERICA 복지포털 `life.hanyang.ac.kr`의 공개 시설·매장·공지·학식을 대화로 안내합니다. 화면에는 채팅과 입력창, 새 대화 및 이전 대화 목록을 두고 날짜·시설 조건은 질문과 앞선 대화에서 해석합니다. 원본 `playlistSDY/efoo-kakao-bot`에서는 학식 파싱 로직과 회귀 자료만 가져왔으며, 원본 GitHub에는 변경을 전송하지 않았습니다.

## 실행

Python 3.11 이상을 사용하며 이 프로젝트 폴더에서 실행합니다.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

`.env`의 `OPENAI_API_KEY=` 뒤에 키를 입력합니다. 생성 모델은 `gpt-6.1-terra`, 임베딩 모델은 `text-embedding-3-small` 1536차원입니다. 사용 가능한 다른 모델을 선택하려면 계정의 정확한 모델 ID로 `OPENAI_MODEL`을 바꿉니다. 키를 프런트엔드나 Git에 넣지 않습니다.

```bash
python -m app.cli collect --full --index
uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

[로컬 화면](http://localhost:8000)에서 사용할 수 있습니다. 키가 없거나 선택한 자료의 인덱스가 미완성이면 명시적인 자료 조회 미리보기로 동작합니다. 이 모드를 AI 답변이나 임베딩 검색으로 표시하지 않습니다.

## 수집 범위

2026년 11월 13~14일 실제 공개 페이지를 기준으로 다음을 보관했습니다. 모든 자료에는 원문 URL과 수집 시각을 남깁니다.

| 자료 | 수집 내용 |
| --- | --- |
| 시설·매장 48곳 | 구내식당, 일반음식점, 카페/베이커리, 편의점, 인쇄/문구/서점/기념품, 자동판매기, 생활서비스 |
| 시설 상세 | 이름·분류·위치·건물번호·연락처·영업시간과 조건·운영 공지·상세 HTML과 텍스트·대표/설명 이미지 |
| 식당 4곳 | 선택한 날짜 및 원문에 표시된 일주일 식단, 메뉴·반찬·가격·태그·이미지·구매 버튼과 수집 당시 판매 표시 |

| 부가 자료 | 전체 HTML, 메타 태그, 모든 링크·이미지·스크립트·스타일·폼/버튼 속성의 감사 목록 |

현재 확인 자료는 **48개 시설, 날짜별 식단 스냅샷 83개, 실제 메뉴 122개, 공지 1건, 일반 안내 3건, 공개 구매 관찰 자료 1건, 이미지 파일 115개**입니다. 공식 공지 목록을 확인한 검증 자료 1건도 별도로 보관합니다. 식단 범위는 4개 식당의 11월 8~27일과 학생식당의 11월 28~30일이며, 미등록 확인도 별도 스냅샷으로 보관합니다. 총 471개 청크를 실제 OpenAI API로 임베딩했습니다. 이후 질문과 정기 수집에 따라 이 수치는 늘어날 수 있습니다.

카탈로그의 모든 공개 필드와 다국어 값, 사이트 UI·구매 관련 필드도 원문과 JSON에 보관합니다. 실제 답변에는 시설 안내·공지·날짜별 메뉴처럼 관련 있는 본문을 색인하며 내비게이션·로그인 위젯·관리용 표시 필드를 사실 근거로 섞지 않습니다. 외부 CSS/JS/폰트는 참조 목록에 기록하고 내려받아 실행하지 않습니다. 전체 웹사이트를 오프라인으로 복제하는 기능은 아닙니다.

이미지 다운로드는 공식 호스트와 허용 경로, MIME 및 파일 서명을 검사합니다. 파일당 10MiB, 실행당 최대 150개·100MiB를 적용하고 동일 URL/내용은 캐시합니다. SVG·실행 콘텐츠·외부 미디어는 목록에 남기며 채팅에 제공하지 않습니다. 이미지 속 글자에는 OCR/Vision을 적용하지 않았으므로 텍스트로 없는 내용을 사진만 보고 답하지 않습니다.

[수집 항목 감사](docs/source-audit.md)에 실제 필드, 4개 식당의 정확한 운영 정보, 페이지 구조와 보관 범위를 정리했습니다. 공개 접근 가능 여부와 별개로 대외 서비스 운영 시 원문과 사진의 이용 조건을 확인해야 합니다.

## 수집 명령

```bash
# 오늘의 4개 식당과 시설 정보 갱신
python -m app.cli collect
# 공개 포털 시설 전체·공지·원본 이미지·주간 메뉴까지 수집하고 임베딩
python -m app.cli collect --full --index
# 지정 날짜, 일부 식당만
python -m app.cli collect --date 2026-11-13 --restaurants re12 re13
# 이미 수집한 일주일 식단의 날짜별 실제 사진 보완
python -m app.cli enrich-images --date 2026-11-08 --days 7 --index
# 원하는 기간의 최신성 확인, 필요한 수집과 범위별 임베딩
python -m app.cli refresh --start 2026-11-16 --end 2026-11-22
# 수집한 변경분만 임베딩
python -m app.cli index
python -m app.cli status
```

`--full`은 공개 시설 목록의 실제 ID와 링크를 따라 구내식당 `detail.php`, 일반 매장 `shop-detail.php`, 홈과 공지·판매처 안내를 수집합니다. 로그인·마이페이지·주문·결제 동작은 수행하지 않습니다. 기존 자료는 각 시설·날짜·페이지 단위로 성공했을 때만 교체합니다. 동일한 내용의 벡터는 유지하고 바뀐 청크만 다시 임베딩합니다. 메뉴를 갱신해도 시설 안내 문서는 지워지지 않습니다.

주간 메뉴의 텍스트에는 사진이 빠질 수 있어 `--full`은 공개된 주간 범위의 일별 페이지도 확인합니다. `enrich-images`는 기존 식단의 선택 날짜와 식당만 다시 방문하고 일별 사진을 보완합니다. 사진만 바뀐 청크의 기존 임베딩은 유지합니다. 공식 일별 페이지에 사진이 없으면 첨부하지 않습니다.

공통 UI에 사용되는 `mock-data.js`나 주석의 예시 연락처는 실제 학교 정보의 근거로 사용하지 않습니다. 비어 있는 필드는 비어 있다고 보관합니다. 예를 들어 창업보육센터식당의 석식 **19시 영업 종료와 18시 30분 배식대 마감**을 구분합니다. 판매 종료·품절·재고는 관찰 시각의 표시이며 현재 상태를 보장하지 않습니다.

## 대화 저장과 복원

질문·답변·출처·사진·응답 모드를 서버 DB의 `chat_sessions`, `conversations`, `chat_messages`에 저장합니다. 새로고침하거나 같은 브라우저로 재접속하면 마지막 대화를 복원하고, **이전 대화**에서 저장한 다른 대화를 다시 열 수 있습니다. **새 대화**는 새 기록을 만들며 이전 기록은 보존합니다. 로그인 계정은 없으므로 브라우저의 식별 쿠키가 삭제되거나 다른 브라우저·기기를 사용하면 같은 사용자로 연결되지 않습니다.

브라우저는 메시지 본문과 대화 ID·요청 ID만 보냅니다. 서버가 본인 소유 대화인지 검사하고 저장된 최근 12개 메시지로 문맥을 구성합니다. 실제 생성 모델에는 그중 최대 8개 메시지를 전달하며, 화면의 전체 저장 기록과 모델이 한 번에 참고하는 범위는 다릅니다. 대화 내용은 공개 시설·메뉴 임베딩 문서에 섞지 않습니다.

사용자·답변 한 쌍을 트랜잭션으로 저장하고 같은 요청 ID를 재전송해도 중복 저장하거나 모델을 다시 호출하지 않습니다. 이전 대화의 늦은 응답이 새 대화를 덮어쓰지 않습니다. 이전 날 작성한 “내일”은 작성 당시 한국 날짜를 기준으로 내부 문맥에서 해석하며 원문은 그대로 보관합니다. 모델 생성은 현재 단일 서버 프로세스에서 대화별로 순서를 맞추며 여러 서버에서 생성까지 직렬화하려면 분산 잠금이 필요합니다.

## 검색과 답변

### 모델이 대화와 자료 도구를 선택

API 키가 있으면 OpenAI Responses API의 네이티브 함수 호출로 대화합니다. 모델은 최근 대화와 한국 현재 시각을 보고 일상 대화, 추가 질문, 시설 탐색, 학교 정보 조회 중 필요한 행동을 선택합니다. `배고파`처럼 간접적으로 필요를 말해도 정해진 문구로 분기하지 않습니다. 먹을 곳을 찾는 맥락이면 식사 후보와 공식 운영 안내를 살펴보고, 단순 공감이나 잡담을 원하면 도구 호출 없이 자연스럽게 답할 수 있습니다.

서버에서 실행할 수 있는 자료 도구는 다음 세 가지입니다.

| 도구 | 역할 |
| --- | --- |
| `facilities` | 분류·위치에 맞는 모든 후보의 공식 설명·운영 공지와 서비스 근거를 확인합니다. 상호에 상품명이 없는 복합 판매점도 비교하며, 미확인 상세는 구분합니다. |
| `facility_details` | 실제 시설 ID로 위치·연락처·운영시간·사진과 설명을 조회합니다. 오래된 자료를 갱신하고, 뒤이은 확인에서 변경되거나 실패한 이전 출처는 재인용하지 않습니다. |
| `school_query` | 개수·시설·학식·공지 질문을 전체 목록 조회, 최신성 확인 및 RAG에 위임합니다. 검증된 답변은 직접 반환하며, 근거 없는 검색 결과는 모델에 돌려 다른 탐색이나 확인 불가 안내를 선택하게 합니다. |

시설 탐색 뒤 상세를 확인하는 것처럼 여러 단계를 이어갈 수 있습니다. 도구 인수와 시설 ID는 서버에서 검증하고, 이번 턴의 도구가 제공한 출처 ID만 인용하도록 확인합니다. 일상 대화에는 출처를 붙이지 않으며, 학교 사실을 안내하는 답변에는 공식 출처와 검증된 사진을 표시합니다. 출처 ID 검증은 모든 문장의 사실성을 자동으로 증명하지는 않습니다.

예를 들어 문구 관련 매장을 찾으면 대학서적처럼 공식 안내에 문구 판매가 있는 곳도 포함합니다. 복합 분류 자체를 모든 상품의 판매 근거로 삼지 않으며, 문구류 취급을 특정 샤프심의 현재 재고로 바꾸지 않습니다. 목록 전체의 사진 대신 실제 선택한 시설의 사진만 표시합니다.

현재 시각은 서버의 `Asia/Seoul` 시각을 사용합니다. 지금 먹을 곳을 제안할 때 공식 요일·운영시간·휴식시간과 대조하도록 지시하지만 실제 개점·휴무·재고·좌석을 실시간으로 확인하는 기능은 아닙니다. 적용 요일이나 휴일 조건을 확인하지 못하면 그 한계를 안내합니다. `school_query`에 전달하는 질문에서도 사용자의 날짜·시설 조건을 보존하며, 실제 수집과 기간 검증은 기존 서버 흐름에서 수행합니다.

```dotenv
AGENTIC_ENABLED=true
AGENTIC_MAX_TURNS=5
```

`AGENTIC_MAX_TURNS`는 한 요청의 모델 응답 반복 상한이며 1~8 사이로 설정합니다. 마지막 회차는 추가 도구 호출 없이 답하도록 제한합니다. `AGENTIC_ENABLED=false`로 바꾸면 기존 학교 정보 조회 흐름을 사용합니다. 설정을 바꾸면 서버를 재시작합니다. `GET /api/status`의 `agentic_enabled`에서 사용 여부를 확인할 수 있습니다.

### 근거에 기반한 학교 정보 조회

시설의 **개수·전체 목록·분류별 집계**는 검색된 일부 문서로 세지 않습니다. 공식 전체 시설 카탈로그의 `records`를 시설 ID 기준으로 집계하고 분류·브랜드·건물·층 필터를 적용합니다. `학교에 편의점 몇개있어?`, `세븐일레븐은 몇 군데야?`, `학생복지관에 편의점 몇 개 있어?`, `학교 시설 종류별로 몇 개 있어?`, `카페 어디 있어?`를 지원합니다. 같은 브랜드의 여러 지점은 각각 유지하고, 공개 목록의 내부 `inactive` 필드로 임의 제외하지 않습니다. 결과는 공식 포털 등록 범위라고 명시하며 전체 목록의 출처·수집 시각·선택한 매장과 위치를 함께 제공합니다.

카탈로그가 없거나 기본24시간을 넘으면 전체 시설 페이지 한 곳만 다시 확인합니다. 구조가 잘못됐거나 수집에 실패하면 정확한 현재 개수를 단정하지 않습니다. 새 카탈로그로 바뀐 청크는 해당 문서 범위만 백그라운드에서 임베딩하며, 정확한 집계 답변 자체에는 모델이 숫자를 추정하거나 계산할 필요가 없습니다. `카페/베이커리` 같은 복합 분류는 그 분류 전체임을 표시하고, 서점만 물었을 때 인쇄·문구·서점·기념품 전체를 서점 개수로 답하지 않습니다.

질문은 **대상 시설·요청 항목·조건·이전 대화의 지시 대상**으로 나누어 해석합니다. 위치·연락처·운영시간·건물번호·사진은 시설별 공식 상세 필드를 직접 조회합니다. 두 시설의 위치와 전화번호를 함께 물으면 각 시설의 두 항목과 개별 출처를 모두 제공합니다. 여러 지점이 있는 브랜드는 지점을 보존하고, 없는 연락처는 다른 지점 번호로 대신하지 않습니다. 현재 영업 여부는 실시간 확인할 수 없다고 구분하며, 토요일을 물었는데 평일 안내만 있으면 토요일 적용 여부를 확인하지 못했다고 표시합니다.

위치·전화와 공지·결제를 함께 물으면 지정한 모든 시설의 상세와 관련 공지를 함께 검색합니다. 모델이 빠뜨린 기본 항목은 인용 가능한 공식 필드로 보완하고, 확인 못한 항목은 시설별로 표시합니다. 공지 제목은 문서 참조로 분리하므로 제목 안의 건물명·날짜·전화 같은 단어를 사용자의 검색 조건으로 오인하지 않습니다. 게시판 확인 실패가 독립적으로 확인한 시설 정보까지 지우지 않으며, 시설 상세 운영 안내와 별도 게시판 공지를 구분합니다.

대화에는 답변에 선택한 시설 ID와 원래 목록의 순서를 함께 저장합니다. `거기 전화번호는?`, `그중 2층만`, `첫 번째`, `나머지는?` 같은 후속 질문을 같은 시설에 연결하고, 여러 시설을 가리켜 모호하면 먼저 대상을 묻습니다. 새 시설이나 분류를 물으면 새 조건으로 바꿉니다. 시설 이름에 들어간 건물명을 별도의 위치 조건으로 오인하지 않도록 같은 이름 해석 규칙을 공유합니다.

`은행` 같은 일반 별칭은 미등록 고유명 내부의 부분 일치로 사용하지 않습니다. 수집 목록에 없는 `우리은행`을 신한은행으로, `CUBIC`을 CU로 대신하지 않고 요청한 시설을 확인하지 못했다고 안내합니다. 이는 해당 시설이 실제로 존재하지 않는다는 단정과 구분합니다.

분류·업종·브랜드·건물·층 조건은 공통 필터로 처리하며 OR/AND를 구분합니다. `카페나 편의점`, `복사와 출력 모두`를 각각 합집합과 교집합으로 해석합니다. 근거가 없는 Wi-Fi·좌석·흡연 등 조건을 임의로 빼고 추천하지 않습니다. `커피 마실 곳`처럼 이용 목적을 물었을 때 세부 근거가 부족하면 공식 카페/베이커리 분류의 **후보**라는 범위를 표시하고 메뉴나 좌석을 보장하지 않습니다.

`학교에 분식집 찾아줘`처럼 공식 분류보다 좁은 업종을 찾으면 시설 ID로 전체 목록과 상세 안내를 연결합니다. 상호·분류·설명·운영 공지의 동의어를 함께 검사해 상호에 업종이 없는 매장도 찾습니다. 분식은 분식·떡볶이·김밥 관련 안내를 확인하므로 운영 공지에만 분식점이라고 적힌 이모네와 33떡볶이를 함께 찾습니다. 매장 ID를 하드코딩하거나 상위8개 문서만으로 검색을 끝내지 않습니다. 결과에는 해당 문장·시설별 출처·위치·영업시간과 사진을 제공합니다. 카탈로그의 업종 근거와 상세 페이지의 시간·사진은 각각의 출처로 인용합니다.

업종 검색에 필요한 상세 자료가 없거나24시간을 넘으면 해당 공식 시설 페이지를 보완하고 바뀐 시설 문서만 임베딩합니다. 실패한 상세 자료는 검색에서 제외하고 확인 범위를 표시합니다. 모든 상세를 확인했을 때는 일부 검색이라는 안내를 붙이지 않습니다. 부정 문구나 복합 분류 이름만으로 특정 업종을 추천하지 않습니다. 영업시간의 요일·시각 범위는 마크다운 취소선으로 표시되지 않도록 처리하며 코드·URL·실제 취소선 문법은 유지합니다.

메뉴, 시설 안내, 공지, 일반 페이지를 구분해서 검색합니다. 날짜별 식단은 다른 날짜 자료로 대체하지 않고, 시설 안내는 최신으로 수집한 문서를 조회합니다. 학식 질문은 먼저 해당 기간의 각 식당 자료가 최신인지 확인합니다. 자료가 없거나 등록 식단은 기본 6시간, 미등록 식단은 60분이 지났으면 공식 일별 페이지를 다시 확인합니다. 변경된 메뉴 청크만 해당 날짜·식당 범위에서 임베딩하고 답합니다. 현재·미래 자료에는 기본 24시간의 저장소 유효시간 상한도 적용합니다.

설명이 필요한 공지·결제 정책·학식 질문에는 OpenAI 임베딩 검색과 근거 기반 생성을 사용합니다. 일반 학교 정보 검색에는 본문 단어 일치도 함께 반영해 정확한 용어가 있는 근거가 빠지는 것을 줄입니다. 공지·결제 질문은 공식 한국어 공지 목록과 본문을 기본24시간 단위로 다시 확인하고 변경된 공지만 임베딩합니다. 목록에서 사라졌거나 확인에 실패한 공지는 DB 기록을 보존하면서 현재 답변 근거에서 제외합니다. 검증된 빈 게시판과 수집 실패를 구분하고, 실패한 페이지를 공지가 없다는 뜻으로 답하지 않습니다.

### 날짜 범위와 자동 수집

한국 시간의 오늘을 기준으로 날짜를 해석하며 주는 **월요일~일요일**, 기간은 **시작일과 종료일 포함**입니다. 예를 들어 다음처럼 물을 수 있습니다.

- `내일 학식 알려줘`, `모레 학생식당 점심은?`
- `다음주 학식 알려줘`, `지난주/저번주 학식은?`
- `다음주 월요일부터 수요일까지 학생식당 점심 알려줘`
- `11월 16~20일 학식`, `2026-11-16~2026-11-22 식단`
- `내일부터 3일간`, `앞으로 7일 학식`, `다음달 학식`
- `그럼 저녁은?`, `같은 기간으로 다시 알려줘`

API에서는 `start_date`와 `end_date`를 함께 보내 정확한 기간을 지정할 수 있으며 질문의 날짜 표현보다 우선합니다. 날짜를 해석한 결과는 `date_range.start/end`로 응답하고 대화 DB에 보관합니다. 후속 질문과 다른 날 재접속해도 원래 기간을 이어받으며, 수집 도중 자정이나 월요일이 되어도 최초 요청 범위로 답합니다. 없는 날짜·모호한 표현·역순·기간 초과는 날짜를 다시 확인하도록 안내하고 오늘 자료로 대체하지 않습니다.

기간 질문은 OpenAI 임베딩 검색과 짧은 근거 기반 요약에 **요청한 모든 날짜·식당의 검증된 식단 표**를 함께 제공합니다. 단일 질문의 근거 개수 제한 때문에 기간 끝이 빠지지 않습니다. 공식 페이지에서 메뉴가 없는 경우의 `미등록`과 네트워크/파싱 실패의 `확인 실패`를 구분합니다. 갱신에 실패한 식당·날짜의 기존 캐시는 최신 답변에서 제외합니다. 임베딩에 실패하면 최신 수집 내용 조회로 안내하고 AI 검색 완료로 표시하지 않습니다.

동일한 날짜·식당을 여러 요청이 동시에 확인하면 수집을 공유합니다. 수집·임베딩 실패 뒤에는 기본 5분 동안 반복 요청을 제한하고, 다음 요청이나 예약 실행이 다시 시도합니다. 공식 이미지가 있는 자료는 검증해 보관하고 인용한 답변에 자동 첨부합니다.

서버가 시작되면 백그라운드에서 한 번 확인하고 이후 기본 **60분마다 오늘부터 14일**을 확인합니다. 서버가 실행 중일 때 동작하는 단일 프로세스용 수집기이며 `uvicorn --workers 1`로 실행합니다. 여러 API 워커나 서버 종료 중 실행은 외부 예약 실행기 또는 분산 잠금이 필요합니다. 현재 AWS 예약 실행기를 배포한 것은 아닙니다.

`.env`에서 기간·갱신 주기를 바꾸고 서버를 재시작합니다. 한 번의 질문 범위는 기본 31일이며 상한은 설정으로 변경할 수 있습니다. 정기 수집 일수는 그 상한 이하여야 합니다.

```dotenv
MAX_DATE_RANGE_DAYS=31
MEAL_REFRESH_HOURS=6
MEAL_EMPTY_REFRESH_MINUTES=60
REFRESH_RETRY_MINUTES=5
SCHEDULE_ENABLED=true
SCHEDULE_INTERVAL_MINUTES=60
SCHEDULE_START_OFFSET_DAYS=0
SCHEDULE_DAYS=14
```

예를 들어 정기 범위를 과거 7일부터 향후 6일까지로 바꾸려면 `SCHEDULE_START_OFFSET_DAYS=-7`, `SCHEDULE_DAYS=14`로 설정합니다. 실행 상태·마지막 처리 건수·다음 예정 시각은 `GET /api/status`의 `scheduler`에서 확인할 수 있습니다. 시설·공지 전체 수집은 기존 `collect --full --index`로 갱신하며, 내장 정기 수집과 질문 시 자동 갱신은 날짜별 학식에 적용됩니다.

시설 종류와 전체 목록을 소개하는 질문은 일반 안내 페이지로 범위를 제한해 양의 유사도 순으로 검색합니다. 일반 검색과 메뉴 검색은 코사인 유사도 0.30을 초기 임계값으로 사용합니다. 시설명이나 확인된 별칭으로 대상을 특정한 경우 해당 시설의 소수 안내·공지 문서를 양의 유사도 순으로 검색합니다. 동일 이름의 지점이 여러 곳이면 한 곳으로 임의 결정하지 않습니다. 일반 질문은 최대 8개, 단일 날짜 비교·전체 질문은 최대 32개 근거를 전달하고 범위가 일부이면 이를 고지하도록 지시합니다. 일반적인 “학식”은 모든 식당을 뜻합니다. 여러 날짜의 식단은 날짜·식당별로 근거를 묶어 전체 표를 보존하며 사진·운영시간을 함께 요청해도 메뉴 기간이 누락되지 않습니다. “학시”, “뭐나와아”, 조합이 풀린 한글 자모는 내부에서만 정규화하고 사용자 원문은 유지합니다.

OpenAI Responses API에서 JSON 구조로 답변과 사용한 출처 ID를 받습니다. 없는 출처 ID나 출처 없는 생성 답변은 차단합니다. 이 검사는 모든 문장의 사실성을 자동 증명하지는 않습니다. 출처와 수집 시각은 대화 안에서 펼쳐 볼 수 있고, 실제 본문에서 인용한 자료에 사진이 있으면 따로 요청하지 않아도 검증된 로컬 이미지를 최대 6장 첨부합니다. 이전 저장 답변도 인용된 자료의 사진 정보가 있으면 표시합니다.

답변은 친근한 한국어 해요체로 핵심부터 안내합니다. 굵은 글씨·제목·목록·표·코드 등 GFM 마크다운을 렌더링하고 `[S1]` 인용은 공식 출처 링크로 연결합니다. 이전 대화도 같은 방식으로 렌더링합니다. Marked 18.2.0과 DOMPurify 3.4.17을 라이선스와 함께 로컬에 고정해 제공하며, 임의 HTML·외부 이미지·위험한 링크를 제거합니다. 사진은 별도 검증된 갤러리에서만 보여줍니다.

학사·졸업요건·대학 전체 연혁처럼 수집한 복지포털에 없는 정보는 답변할 수 없음을 안내합니다. 메뉴명만으로 알레르기 안전성이나 영양 성분을 추정하지 않습니다.

```text
app/school_context.py 이전 시설·목록·지점·순서 참조 해석

```

원문과 JSON은 `data/raw`, `data/portal`, 이미지는 `data/media`, 검색 데이터는 `data/efoo.sqlite3`에 저장합니다. 웹은 해시로 허용한 미디어만 제공하며 수집 원문 HTML이나 캐시 설정 파일을 공개하지 않습니다.

로컬 SQLite는 임베딩을 저장하고 메타데이터 필터 후 정확 코사인 검색을 합니다. `DATABASE_URL`이 있으면 PostgreSQL pgvector의 `<=>`로 검색합니다. 운영 DB에서는 관리자가 확장을 설치하고 앱의 DDL·수집 권한을 제한해야 합니다. 로컬 초기화는 테이블과 확장을 생성합니다.

## AWS 설계와 Docker

1주차 AWS 설계는 CloudFront + 비공개 S3(OAC) 웹, ALB + ECS Fargate API, 비공개 RDS PostgreSQL pgvector, 원문/미디어 S3, EventBridge 예약 수집 태스크, Secrets Manager, CloudWatch입니다. `RAW_S3_BUCKET`은 현재 날짜별 식단 원문을 S3에도 보관하는 어댑터이며, 포털·미디어 전체의 S3 동기화는 후속 구현 대상입니다.

2주차에는 [환경 검증용 API](deploy/aws-test/README.md)를 별도로 배포했습니다. 서울 리전의 전용 ECR·비공개 S3·VPC·ALB·ECS Fargate와 IAM 실행/업무 역할, CloudWatch Logs를 구성했습니다. Fargate 작업 1개, ALB healthy, `/healthz`와 `/api/environment`의 HTTP 200, S3 실제 읽기를 포함한 12개 검증을 통과했습니다. 로그 보존은 실제 14일로 확인했습니다.

이 API는 공식 출처 메타데이터 2건으로 환경 연결을 확인하며 `rag_enabled=false`를 표시합니다. 전체 챗봇의 RDS·모델·대화·미디어를 AWS에 이관한 상태는 아닙니다. 실습은 NAT 없이 Public Fargate를 사용하고 작업의 TCP 8000은 ALB 보안 그룹만 허용합니다. 1주차의 private Fargate/NAT와 차이가 있습니다.

[AWS 환경 확인 웹](https://docknwx8xl49w.cloudfront.net)은 별도 CloudFront 스택의 HTTPS 접속점입니다. 웹과 `/healthz`, `/api/environment` 모두 실제 HTTP 200 및 동일 빌드 버전을 확인했습니다. CloudFront는 캐시하지 않고 ALB로 전달하며, 이번 실습의 CloudFront→ALB 구간은 HTTP입니다. 정적 웹 S3/OAC·ALB HTTPS·인증은 본 서비스 배포 단계에서 구성해야 합니다. ALB와 Fargate 등은 실행 중 비용이 발생하며, 실습 리소스에는 자동 삭제를 적용하지 않았습니다.

```bash
cp .env.example .env
# .env에 OpenAI 키 설정 후
docker compose up --build -d
docker compose exec web python -m app.cli collect --full --index
```

PostgreSQL용으로 `.env`에 `POSTGRES_PASSWORD`를 정하고 다음을 실행할 수 있습니다.

```bash
docker compose -f compose.yaml -f compose.postgres.yaml up --build -d
```

로컬 PostgreSQL·pgvector의 실제 벡터 저장·검색과 필터를 검증했습니다. 앱 Docker 이미지 실행, RDS/S3/AWS 운영 배포는 별도 검증 대상입니다.

## API와 검증

- `GET /healthz`: 실행 상태
- `GET /api/status`: 수집 범위·청크·임베딩 준비 상태·`agentic_enabled`
- `GET /api/facilities`: 수집한 시설 안내와 출처
- `GET /api/meals?date=2026-11-13`: 날짜별 수집 메뉴
- `GET /api/conversations/current`: 현재 브라우저 대화와 저장 메시지 복원
- `GET /api/conversations`: 본인 대화 목록
- `POST /api/conversations`: 새 대화 생성
- `GET /api/conversations/<id>`: 본인 대화 전환과 기록 조회
- `POST /api/chat`: `{ "message": "내일 학식 뭐나와", "conversation_id": "대화 UUID", "turn_id": "요청 UUID" }`
- 정확한 기간은 위 요청에 `"start_date":"2026-11-16", "end_date":"2026-11-22"`를 함께 추가합니다.
- 이전 클라이언트의 `message/history` 요청도 호환하지만 새 웹은 서버에 저장된 이력을 사용합니다.
- `GET /media/<sha256>.<extension>`: 검증된 수집 파일

전체 수집과 강제 갱신은 관리자 CLI로 제공하고, 학식 질문·내장 예약 실행에서는 검증된 날짜 범위만 서버 내부에서 자동 갱신합니다. 공개 운영 시 인증과 사용자별 요청 한도 정책은 별도로 구성해야 합니다. 질문·답변·키를 앱 로그에 남기지 않습니다. 대화 기록은 서버 DB에 저장하고 같은 브라우저의 HttpOnly 쿠키로 본인 기록만 복원합니다. Responses 요청은 `store=False`를 사용합니다.

```bash
pip install -r requirements-dev.txt
python -m pytest -q
```

실제 API로 학교 우체국 위치/시간, 창업보육센터 배식대 마감, 결제 공지, 시설 사진 및 학식 답변을 확인했습니다. 자료 없는 졸업요건 질문은 근거 부족으로 처리했습니다. [검증 기록](docs/verification.md)을 참고하세요.

2026년11월19일에는 에이전트·복합 판매점·출처 변경·검색 복구 검사를 추가해 Python 1000개와 하위검사21개가 통과했습니다. AWS 검증 앱의 독립 검사6개와 UI DOM 검사49개도 통과했습니다. 실제 모델로 일상 대화, 배고픔에 따른 시설 탐색, 샤프심을 살 곳, 문구점 전체 조회, 복지관 후속 질문, 기념품·교재 복합 질문을 확인했습니다.
